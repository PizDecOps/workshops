## Блок 1: Liveness & Readiness Probes - Здоровье приложения

### Текст для выступления

В мире Production мы не можем доверять приложению только потому, что его процесс запущен. Приложение может "зависнуть" внутри (`Deadlock`) или еще не успеть загрузить тяжелые кэши из базы.

Для этого в K8s есть два основных механизма:

- **Liveness Probe:** Отвечает на вопрос "Жив ли ты?". Если проверка провалена - K8s убивает контейнер и перезапускает его. Это защита от зависаний.
- **Readiness Probe:** Отвечает на вопрос "Готов ли ты принимать трафик?". Если проверка провалена - Pod исключается из балансировщика (`Service/Ingress`). Это защита от отправки запросов в еще не загрузившееся приложение.

### Живое демо

Создадим Pod с проверками:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: health-check-demo
spec:
  containers:
    - name: app
      image: nginx
      livenessProbe:
        httpGet:
          path: /index.html
          port: 80
        initialDelaySeconds: 5 # Даем 5 секунд на старт
        periodSeconds: 5 # Проверяем каждые 5 сек
      readinessProbe:
        tcpSocket:
          port: 80
        initialDelaySeconds: 2
        periodSeconds: 10
```

Проверим статус пода и события:

```bash
kubectl describe pod health-check-demo
```

### Вопросы

- В: Что будет, если настроить `Liveness Probe` на тяжелый запрос, который долго отвечает?
  - О: K8s может войти в "цикл рестартов" (`CrashLoopBackOff`), убивая приложение раньше, чем оно успеет ответить.
- В: Что будет, если один контейнер в поде упадет?
  - О: Kubernetes перезапустит именно упавший контейнер внутри пода (согласно `RestartPolicy`), сам `Pod` останется на месте.

## Блок 2: Resource Management - Requests vs Limits

### Текст для выступления

Без ограничений один "прожорливый" Pod может съесть все ресурсы ноды и убить соседей. В K8s есть два типа настроек ресурсов:

- **Requests (Запросы):** Минимум, который гарантирован поду. На основе этого значения Scheduler выбирает ноду.
- **Limits (Лимиты):** Потолок. Больше этого значения под съесть не сможет.

**Важно:** CPU - это сжимаемый ресурс (его просто "подрежут"), а RAM - несжимаемый. Если под превысит лимит по RAM, он будет убит по ошибке `OOMKilled` (Out Of Memory).

### Живое демо

Посмотрим на описание ресурсов в манифесте:

```yaml
spec:
  containers:
    - name: db
      image: postgres
      resources:
        requests:
          memory: "64Mi"
          cpu: "250m" # 0.25 ядра
        limits:
          memory: "128Mi"
          cpu: "500m" # 0.5 ядра
```

Посмотрим реальное потребление ресурсов (нужен metrics-server)

```bash
kubectl top pods
```

### Вопросы

- В: Может ли под использовать больше ресурсов, чем указано в `Requests`?
  - О: Да, если на ноде есть свободное место, но только до границы `Limits`.
- В: Что произойдет, если на ноде закончится память, а лимиты еще не достигнуты?
  - О: Kubelet начнет выселять (`Eviction`) поды, начиная с тех, у кого нет лимитов или они сильно превышают свои `Requests`.

## Блок 3: QoS Classes - Приоритеты выживания

### Текст для выступления

В Kubernetes недостаточно просто запустить под. Нужно понимать, насколько "ценным" этот под является для кластера. Когда на ноде заканчиваются ресурсы (особенно память), Kubelet должен решить: кого убить первым, чтобы спасти саму ноду?

Для этого существуют **QoS-классы (Quality of Service)**. Вы не указываете их вручную - Kubernetes сам присваивает их поду, глядя на то, как вы заполнили `requests` и `limits`.

1. Guaranteed (Высший приоритет)

   Это "VIP-поды". Они самые предсказуемые и стабильные.
   - **Условие:** `requests` и `limits` указаны для всех ресурсов (CPU и RAM) и они строго равны.
   - **Поведение:** `Kubelet` выделяет им четко очерченную область ресурсов. Их убивают последними, только если нода вот-вот "умрет" целиком.

2. Burstable (Средний приоритет)
   - **Условие:** Указаны хотя бы `requests` (или `requests < limits`).
   - **Поведение:** Под имеет гарантированный минимум, но может "раздуваться" до лимитов, если на ноде есть место. Если ноде станет плохо, Burstable-поды начнут выселять, если они потребляют больше, чем их `requests`.

3. BestEffort (Низший приоритет)

   Это "поды-бездомные".
   - **Условие:** Вообще не указаны ни `requests`, ни `limits`.
   - **Поведение:** Живут на "сдачу" от других подов. Как только ноде требуется хоть капля ресурсов для более приоритетных задач, BestEffort-поды убиваются мгновенно и безжалостно.

### Живое демо

Давайте создадим три разных пода и посмотрим, как K8s распределит их по классам.

1. Создаем манифест `qos-demo.yaml`:

   ```yaml
   ---
   apiVersion: v1
   kind: Pod
   metadata:
     name: qos-guaranteed
   spec:
     containers:
       - name: nginx
         image: nginx
         resources:
           requests:
             cpu: "100m"
             memory: "100Mi"
           limits:
             cpu: "100m"
             memory: "100Mi"
   ---
   apiVersion: v1
   kind: Pod
   metadata:
     name: qos-burstable
   spec:
     containers:
       - name: nginx
         image: nginx
         resources:
           requests:
             memory: "50Mi"
   ---
   apiVersion: v1
   kind: Pod
   metadata:
     name: qos-best-effort
   spec:
     containers:
       - name: nginx
         image: nginx
   ```

2. Применяем и проверяем статус:

   ```bash
   kubectl apply -f qos-demo.yaml

   # Магия фильтрации jsonpath, чтобы увидеть только имена и классы
   kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
   ```

### Вопросы

- В: Почему важно делать базу данных (PostgreSQL/Redis) классом `Guaranteed`?
  - О: База данных очень чувствительна к внезапным рестартам. Если её выселит Kubelet из-за `соседа-BestEffort`, вы получите простой и потенциально поврежденные данные.
- В: Что будет, если у одного контейнера в поде указаны лимиты, а у другого - нет?
  - О: Весь Pod станет `Burstable`. Для `Guaranteed` нужно, чтобы каждый контейнер внутри имел четкие и равные лимиты/запросы.
- В: Кто принимает решение об убийстве пода при нехватке памяти (OOM)?
  - О: Ядро Linux через `OOM Killer`, но Kubernetes помогает ему, выставляя подам `oom_score_adj` на основе их QoS-класса. У `BestEffort` этот счетчик максимальный (их убьют первыми).

## Блок 4: Ingress Controllers (L7) - Сетевой регулировщик

### Текст для выступления

В прошлых модулях мы использовали **Services** (`ClusterIP`, `NodePort`, `LoadBalancer`). Это уровень L4: мы пробрасывали "трубу" от порта до порта. Но в реальном продакшене у нас сотни сервисов, и давать каждому свой внешний IP (LoadBalancer) - это дорого, а управлять портами NodePort - безумие.

Для решения этой проблемы существует Ingress.

**Как это работает:**

1. **Ingress Controller:** Это приложение (обычно `Nginx`, `HAProxy` или облачный `ALB`), которое постоянно запущено в кластере. Оно является "единым входом" для всего внешнего трафика.
2. **Ingress Resource:** Это правила, которые мы пишем, чтобы сказать контроллеру: "трафик с доменом `shop.com` отправляй в сервис `frontend`, а `shop.com/api` - в сервис `backend"`.

#### Nginx vs ALB (Облачные контроллеры)

- **Nginx Ingress:** Самый популярный. Живет прямо внутри вашего кластера. Весь трафик сначала попадает в поды Nginx, а они распределяют его дальше.
- **ALB (AWS) / Google Cloud Load Balancer:** Контроллер не гоняет трафик через себя, а управляет "железным" балансировщиком провайдера. Когда вы создаете Ingress-ресурс, облако само настраивает свои внешние таргет-группы.

### Живое демо

Поскольку установка контроллера зависит от окружения, мы рассмотрим установку самого популярного решения - `ingress-nginx`.

1. Установка контроллера одной командой:

   ```bash
   # Для Bare-metal или локальных кластеров
   kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.8.2/deploy/static/provider/cloud/deploy.yaml
   ```

2. Проверка запуска:

   Контроллер создает свой собственный Namespace. Нам нужно дождаться, когда LoadBalancer получит внешний IP.

   ```bash
   # Ждем появления EXTERNAL-IP
   kubectl get svc -n ingress-nginx
   ```

3. Как убедиться, что он работает?

   Попробуем просто постучаться на внешний IP контроллера.

   ```bash
   # Если вы видите "404 Not Found" от nginx - это отличный знак!
   # Значит, контроллер жив, но мы еще не написали для него правил.
   curl http://<EXTERNAL-IP>
   ```

### Вопросы

- В: Почему нельзя просто выставить Nginx как обычный `Deployment` с `NodePort`?
  - О: Можно, но `Ingress Controller` делает больше: он динамически обновляет конфиги без перезагрузки при появлении новых подов, умеет в SSL-терминацию и интегрируется с K8s API.
- В: Что будет, если `Ingress Controller` упадет?
  - О: Весь внешний доступ к вашим приложениям пропадет. Поэтому в проде контроллер запускается минимум в 2-3 репликах с настройкой `PodAntiAffinity` (разберем в Блоке 6).
- В: Можно ли запустить несколько разных `Ingress-контроллеров` в одном кластере?
  - О: Да. Для этого используется `ingressClassName`. Например, один контроллер для внешнего трафика, другой - только для внутренних корпоративных сервисов.

## Блок 5: Ingress Resources - Виртуальные хосты и TLS

### Текст для выступления

Теперь, когда у нас есть "входная дверь" (Контроллер), нам нужно объяснить ей, как сортировать гостей. `Ingress Resource` - это объект, в котором мы описываем правила маршрутизации.

Основные задачи этого блока:

1. **Host-based Routing:** Когда у нас один IP, но много доменов. Запрос на `api.com` идет в один сервис, а `web.com` - в другой. Контроллер понимает это по HTTP-заголовку `Host`.
2. **Path-based Routing:** Когда внутри одного домена нужно разделить трафик. Например, `/images` - на хранилище, а `/login` - на сервис аутентификации.
3. **TLS Termination (SSL):** Мы не хотим настраивать сертификаты в каждом микросервисе. Мы отдаем их Ingress-контроллеру. Он расшифровывает HTTPS и передает внутрь кластера обычный HTTP.
4. **Cert-manager:** Это стандарт индустрии для автоматизации. Он сам общается с Let's Encrypt, проходит проверки, выписывает сертификаты и обновляет их до того, как они протухнут.

### Живое демо

Давайте создадим "боевой" манифест, который объединяет маршрутизацию и автоматический выпуск SSL-сертификата.

1. Создаем файл `workshop-ingress.yaml`:

   ```yaml
   apiVersion: networking.k8s.io/v1
   kind: Ingress
   metadata:
     name: main-web-ingress
     annotations:
       # Самая важная аннотация для интеграции с cert-manager
       cert-manager.io/cluster-issuer: "letsencrypt-prod"
       # Опционально: принудительный редирект с http на https
       nginx.ingress.kubernetes.io/ssl-redirect: "true"
   spec:
     ingressClassName: nginx # Указываем, какой контроллер должен обработать этот конфиг
     tls:
       - hosts:
           - workshop.example.com
         secretName: workshop-tls-secret # Сюда cert-manager положит готовый сертификат
     rules:
       - host: workshop.example.com
         http:
           paths:
             - path: /api
               pathType: Prefix
               backend:
                 service:
                   name: backend-service
                   port:
                     number: 8080
             - path: /
               pathType: Prefix
               backend:
                 service:
                   name: frontend-service
                   port:
                     number: 80
   ```

2. Применяем и проверяем статус:

   ```bash
   kubectl apply -f workshop-ingress.yaml

   # Проверяем, что Ingress получил IP от контроллера
   kubectl get ingress

   # Следим за процессом выпуска сертификата
   kubectl get certificate
   kubectl describe certificate workshop-tls-secret
   ```

### Вопросы

- В: Что будет, если два Ingress-ресурса используют один и тот же `host`, но разные пути?
  - О: Контроллер (`Nginx`) склеит их в один большой конфиг. Это удобно для распределенной разработки, но нужно следить, чтобы пути не пересекались.
- В: В чем разница между `pathType: Prefix` и `Exact`?
  - О: `Prefix` сопоставляет начало (напр. `/api` поймает и `/api/v1`), а `Exact` требует полного совпадения. В 99% случаев используется `Prefix`.
- В: Зачем нам `secretName` в секции TLS, если мы используем cert-manager?
  - О: Cert-manager - это сторонний инструмент. Он не "встраивается" в Ingress напрямую. Он видит ваш запрос, выпускает сертификат и сохраняет его в стандартный `Secret` в Kubernetes. А Ingress-контроллер просто берет данные из этого секрета.

## Блок 6: Affinity и Anti-Affinity - Умное размещение подов

### Текст для выступления

Представьте, что вы запустили 3 реплики приложения, но Kubernetes решил поселить их все на одну и ту же ноду. Если эта нода "умрет" (проблемы с питанием или диском), ваше приложение упадет целиком, несмотря на наличие реплик.

Для управления этим процессом существуют механизмы **Affinity** (сродство) и **Anti-Affinity** (отталкивание).

1. **Pod Anti-Affinity:** Позволяет сказать: "Не ставь этот под на ту же ноду, где уже живет такой же под". Это гарантирует, что при падении одной ноды вы потеряете только одну реплику.
2. **Topology Spread Constraints:** Позволяет разносить поды не просто по нодам, а по зонам доступности (Availability Zones). Если в дата-центре целиком упадет стойка или целый зал, ваши поды выживут в другом зале.
3. **Node Affinity:** Позволяет привязать поды к конкретным нодам (например, только к тем, где есть SSD или GPU).

Существует два типа жесткости правил:

- **Required (Hard):** "Сделай только так, иначе не запускай под вообще".
- **Preferred (Soft)**: "Постарайся сделать так, но если не получается - запускай где есть место".

### Живое демо

Давайте напишем Deployment, который гарантирует, что его реплики никогда не окажутся на одной ноде и, по возможности, будут разнесены по разным зонам.

1. Создаем файл affinity-demo.yaml:

   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: ha-app
   spec:
     replicas: 3
     selector:
       matchLabels:
         app: web-ha
     template:
       metadata:
         labels:
           app: web-ha
       spec:
         affinity:
           # ПРАВИЛО: Не ставить поды с лейблом app: web-ha на одну ноду
           podAntiAffinity:
             requiredDuringSchedulingIgnoredDuringExecution:
               - labelSelector:
                   matchExpressions:
                     - key: app
                       operator: In
                       values:
                         - web-ha
                 topologyKey: "kubernetes.io/hostname"

           # ПРАВИЛО: Желательно разнести поды по разным дата-центрам (зонам)
           nodeAffinity:
             preferredDuringSchedulingIgnoredDuringExecution:
               - weight: 100
                 preference:
                   matchExpressions:
                     - key: topology.kubernetes.io/zone
                       operator: In
                       values:
                         - us-east-1a
                         - us-east-1b
         containers:
           - name: nginx
             image: nginx
   ```

2. Проверяем распределение:

   ```bash
   kubectl apply -f affinity-demo.yaml

   # Посмотрим, на каких нодах оказались поды
   kubectl get pods -l app=web-ha -o wide
   ```

### Вопросы

- В: Что будет, если я укажу `required` Anti-Affinity на 5 реплик, а в кластере всего 3 ноды?
  - О: 3 пода запустятся (по одному на ноду), а 2 останутся в статусе `Pending`, так как подходящих нод для выполнения "жесткого" правила больше нет.
- В: Чем `topologyKey` отличается от обычного селектора?
  - О: Он определяет границы "домена отказа". Если это `hostname`, мы разносим по серверам. Если это `topology.kubernetes.io/zone`, мы разносим по дата-центрам.
- В: Влияет ли Affinity на уже запущенные поды?
  - О: Нет. Название `IgnoredDuringExecution` в конфиге означает, что правила проверяются только в момент планирования (`Scheduling`). Если после запуска правила изменятся, Kubernetes не будет переносить поды сам (для этого нужен специальный инструмент - `Descheduler`).

## Блок 7: Taints & Tolerations - Фейс-контроль для нод

### Текст для выступления

Представьте, что у вас в кластере есть дорогая нода с мощными GPU или специальная нода под базу данных с быстрыми дисками. Вы не хотите, чтобы Kubernetes по ошибке закинул туда какой-нибудь легкий `nginx` или `redis-cache`, заняв ценное место.

Для этого используется механизм "отталкивания":

1. **Taint (Окрашивание/Метка):** Мы вешаем на ноду "запрещающий знак". Теперь нода говорит: "Я не принимаю никого, у кого нет специального разрешения".
2. **Toleration (Допуск):** Мы прописываем в Поде специальное разрешение. Это говорит: "Я знаю, что на этой ноде есть ограничение, и мне разрешено на ней находиться".

Эффекты Taints:

- **NoSchedule:** Поды без допуска просто не будут планироваться на эту ноду. (Самый частый вариант).
- **PreferNoSchedule:** Постарайся не ставить сюда поды без допуска, но если больше некуда - ставь.
- **NoExecute:** Если на ноду повесить такой тайт, она немедленно выгонит (`evict`) все поды, у которых нет соответствующего допуска.

### Живое демо

Давайте выделим одну ноду под "Special Workload" (например, только для системных задач) и попробуем туда пробиться.

1. Вешаем Taint на ноду:

   ```bash
   # Формат: kubectl taint nodes <имя_ноды> ключ=значение:эффект
   kubectl taint nodes node-01 specialized=true:NoSchedule
   ```

2. Пытаемся запустить обычный под:

   Если вы попробуете запустить обычный Deployment, вы увидите, что на `node-01` он никогда не попадет.

3. Создаем под с допуском (Toleration):

   Файл `special-pod.yaml`:

   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: special-app
   spec:
     containers:
       - name: nginx
         image: nginx
     # Вот наше разрешение "пройти через фейс-контроль"
     tolerations:
       - key: "specialized"
         operator: "Equal"
         value: "true"
         effect: "NoSchedule"
   ```

4. Проверяем результат:

```bash
kubectl apply -f special-pod.yaml
kubectl get pod special-app -o wide # Он должен оказаться на node-01
```

### Вопросы

- В: Означает ли `Toleration`, что под ОБЯЗАТЕЛЬНО попадет на эту ноду?
  - О: Нет! Это лишь разрешение. Чтобы под попал именно туда, нужно дополнительно использовать `nodeSelector` или `nodeAffinity`. Taints только запрещают, но не притягивают.
- В: Зачем нужен эффект `NoExecute`?
  - О: Он часто используется самой системой. Например, если нода теряет связь с мастером, на неё вешается тайт `node.kubernetes.io/unreachable:NoExecute`, и через пару минут K8s выселяет оттуда все поды, чтобы перезапустить их на живых нодах.
- В: Можно ли повесить несколько `Taints` на одну ноду?
  - О: Да, и тогда поду понадобится список допусков (`Tolerations`) ко всем этим тайнтам, чтобы иметь возможность там запуститься.

## Блок 8: Horizontal Pod Autoscaler (HPA) - Автопилот масштабирования

### Текст для выступления

В реальной жизни нагрузка на приложение никогда не бывает ровной. Утром пользователи заходят почитать новости, вечером - посмотреть видео, а ночью все спят. Если мы всегда будем держать 10 реплик, ночью мы будем зря платить за ресурсы. Если оставим 2 - утром всё упадет.

**HPA (Horizontal Pod Autoscaler)** решает эту проблему. Он работает как термостат:

1. Вы задаете целевой показатель (например, "я хочу, чтобы мои поды были загружены по CPU в среднем на 50%").
2. Контроллер HPA каждые 15 секунд опрашивает `Metrics Server`.
3. Если средняя нагрузка стала 75%, HPA вычисляет, сколько нужно добавить подов, и меняет поле `replicas` в вашем Deployment.

**Формула расчёта:**

```plaintext
desiredReplicas = ceil(currentReplicas * (currentMetricValue / targetMetricValue))
```

**Критическое требование:** `HPA` не может работать, если у подов не указаны Requests (Блок 2). Без них Kubernetes не поймет, от какого числа считать проценты.

### Живое демо

Давайте создадим приложение и заставим его масштабироваться под нагрузкой.

1. Создаем `Deployment` с лимитами:

   Файл `hpa-app.yaml`:

   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: php-apache
   spec:
     selector:
       matchLabels:
         run: php-apache
     replicas: 1
     template:
       metadata:
         labels:
           run: php-apache
       spec:
         containers:
           - name: php-apache
             image: registry.k8s.io/hpa-example
             ports:
               - containerPort: 80
             resources:
               requests:
                 cpu: "200m"
   ```

2. Создаем правило автоматасштабирования:
   Мы скажем: "Держи от 1 до 10 реплик, старайся попадать в 50% потребления CPU".

   ```bash
   kubectl autoscale deployment php-apache --cpu-percent=50 --min=1 --max=10
   ```

3. Имитируем нагрузку (в отдельном терминале):

   ```bash
   kubectl run -i --tty load-generator --rm --image=busybox:1.28 -- restart=Never -- /bin/sh -c "while sleep 0.01; do wget -q -O- http://php-apache; done"
   ```

4. Наблюдаем за магией:

```bash
# Следим, как растет нагрузка и количество реплик
kubectl get hpa php-apache --watch
```

### Вопросы

- В: Почему HPA не сразу удаляет поды, когда нагрузка упала?
  - О: Чтобы избежать "дребезга" (`thrashing`) - ситуации, когда поды то создаются, то удаляются каждую секунду. По умолчанию есть период охлаждения (`stabilization window`), обычно это 5 минут на уменьшение.
- В: Можно ли масштабироваться не по CPU, а, например, по количеству запросов в секунду?
  - О: Да, но для этого нужны кастомные метрики (`Custom Metrics API`), например, через `Prometheus` и `Prometheus Adapter`. Из коробки HPA умеет только в CPU и Memory.
- В: Что будет, если `HPA` захочет 100 реплик, а на нодах нет места?
  - О: Поды создадутся, но зависнут в статусе `Pending`. Для решения этой проблемы нужен уже другой инструмент - `Cluster Autoscaler`, который добавит сами сервера (ноды) в кластер.

## Блок 9: Lifecycle Hooks - PreStop и PostStart

### Текст для выступления

В Kubernetes жизнь контейнера начинается с команды `Entrypoint` и заканчивается сигналом `SIGTERM`. Но иногда приложению нужно "помочь" правильно войти в работу или корректно из неё выйти. Для этого существуют **Lifecycle Hooks** (хуки жизненного цикла).

1. PostStart

   Выполняется сразу после создания контейнера.
   - **Зачем:** Регистрация в сторонних сервисах, настройка прав на файлы, отправка уведомлений о запуске.
   - **Нюанс:** Выполняется параллельно с основной командой (`ENTRYPOINT`). Если хук зависнет или завершится с ошибкой, контейнер будет перезапущен.

2. PreStop

   Выполняется **непосредственно перед** тем, как Kubernetes отправит контейнеру сигнал на выключение (`SIGTERM`).
   - **Зачем:** Главный инструмент для `Graceful Shutdown`. Мы можем приказать приложению закончить обработку текущих запросов, закрыть соединения с базой данных или выгрузить кэш на диск.
   - **Нюанс:** Пока `PreStop` не завершится, сигнал SIGTERM не будет отправлен. Однако всё ограничено таймером `terminationGracePeriodSeconds` (по умолчанию 30 сек).

### Живое демо

Давайте создадим контейнер, который "красиво" прощается перед удалением.

1. Создаем файл `lifecycle-demo.yaml`:

   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: lifecycle-hooks-demo
   spec:
     containers:
       - name: lifecycle-container
         image: nginx
         lifecycle:
           postStart:
             exec:
               command:
                 [
                   "/bin/sh",
                   "-c",
                   "echo 'Hello from PostStart' > /usr/share/nginx/html/start.html",
                 ]
           preStop:
             exec:
               # Логируем время удаления и ждем 15 секунд, чтобы балансировщик успел убрать IP пода
               command:
                 [
                   "/bin/sh",
                   "-c",
                   "echo 'Stopping at $(date)' >> /var/log/stop.log; sleep 15",
                 ]

     # Даем контейнеру достаточно времени на выполнение preStop
     terminationGracePeriodSeconds: 45
   ```

2. Применяем и проверяем:

   ```bash
   kubectl apply -f lifecycle-demo.yaml

   # Проверим, что PostStart сработал
   kubectl exec lifecycle-hooks-demo -- cat /usr/share/nginx/html/start.html
   ```

3. Имитируем удаление и наблюдаем за временем:

   ```bash
   # В одном терминале запустим лог
   kubectl logs -f lifecycle-hooks-demo

   # В другом - удалим под
   kubectl delete pod lifecycle-hooks-demo
   ```

Вы заметите, что команда `delete` "зависнет" на 15 секунд. Это и есть работа `PreStop-хука`.

## Блок 10: Graceful Shutdown - Искусство мягкого прощания

### Текст для выступления

Когда мы обновляем приложение (`Rolling Update`), Kubernetes удаляет старые поды и создает новые. Проблема в том, что удаление пода - это процесс, который происходит в нескольких компонентах кластера параллельно, а не последовательно.

Что происходит при удалении пода (`kubectl delete`):

1. **Control Plane** меняет статус пода на `Terminating`.
2. **Endpoint Controller** узнает об этом и удаляет IP пода из списка `Endpoints` (сервисы больше не шлют трафик).
3. **Kubelet** на ноде получает команду и начинает процесс остановки контейнера (запускает `PreStop-хук` и шлет `SIGTERM`).
4. **Ingress Controller** (Nginx) получает обновление от API и перегенерирует свой конфиг.

#### В чем подвох?

Обновление конфига Nginx или облачного балансировщика занимает время (1-5 секунд). Если ваш контейнер получит `SIGTERM` и мгновенно завершит работу, Ingress может всё еще пытаться отправить на него пару последних запросов. Результат - ошибка 502 у клиента.

**Решение - Graceful Shutdown:**
Мы должны заставить контейнер "подождать" пару секунд после получения команды на удаление, чтобы сеть успела перестроиться.

### Живое демо

Давайте настроим "идеальный" Graceful Shutdown для Nginx.

1. Создаем манифест graceful-deployment.yaml:

   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: graceful-app
   spec:
     replicas: 3
     selector:
       matchLabels:
         app: web
     template:
       metadata:
         labels:
           app: web
       spec:
         # Важно: даем поду достаточно времени на все маневры
         terminationGracePeriodSeconds: 40
         containers:
           - name: nginx
             image: nginx
             ports:
               - containerPort: 80
             lifecycle:
               preStop:
                 exec:
                   command:
                     - /bin/sh
                     - -c
                     # 1. Ждем 15 секунд, пока Ingress уберет нас из балансировки
                     # 2. Посылаем сигнал завершения самому nginx
                     - "sleep 15 && nginx -s quit"
   ```

2. Проверка "бесшовности":

   Чтобы реально увидеть это в бою, запустите бесконечный цикл запросов к вашему Ingress:

   ```bash
   while true; do curl -I -s http://workshop.example.com | grep HTTP; sleep 0.1; done
   ```

   Затем в другом терминале сделайте рестарт деплоймента:

   ```bash
   kubectl rollout restart deployment graceful-app
   ```

   Если всё настроено верно, в логе `curl` не должно появиться ни одной ошибки 502.

### Вопросы

- В: Чем отличается `SIGTERM` от `SIGKILL`?
  - О: `SIGTERM` - это вежливая просьба "закройся, пожалуйста". Приложение может его поймать и завершить дела. `SIGKILL` - это выстрел в голову от ядра ОС, приложение умирает мгновенно, не успев ничего сохранить.
- В: Нужно ли добавлять `sleep` в `preStop`, если моё приложение написано на Go/Java и само ловит `SIGTERM`?
  - О: Да, желательно. Даже если приложение "умное", оно не знает, что `Ingress Controller` на другом конце кластера еще не успел обновить свои таблицы маршрутизации. Пауза в 5-10 секунд гарантирует чистоту трафика.
- В: Поможет ли Graceful Shutdown при падении всей ноды целиком?
  - О: Нет. Если нода выключилась физически, `preStop` не запустится. Это сработает только при плановом удалении подов (деплой, скейлинг, команда `drain`).
