## Блок 1: Ephemeral vs Persistent - Жизненный цикл данных

### Текст для выступления

Контейнеры по своей природе - это временные сущности. Если процесс внутри контейнера упадет или вы обновите версию приложения, файловая система контейнера будет сброшена до исходного состояния (образа). Все логи, загруженные картинки или базы данных исчезнут.

1. **Ephemeral (Эфемерное):** Данные живут столько же, сколько сам Pod.
   - Главный представитель - **emptyDir**. Это пустая папка, которая создается на диске ноды в момент запуска Пода.
   - **Зачем это нужно?** Для кэширования, хранения временных промежуточных данных или обмена файлами между контейнерами внутри одного Пода (Sidecar-паттерн).
   - **Плюс:** Это очень быстро, так как работа идет с локальным диском сервера. Можно даже заставить Kubernetes создать эту папку в оперативной памяти (`RAM`), если данных мало, но скорость нужна запредельная.

2. Persistent (Постоянное): Данные живут дольше Пода.
   - Если Под удаляется, переезжает на другую ноду или кластер обновляется - данные на сетевом диске сохраняются.
   - В этом случае Kubernetes работает не с папками на сервере, а с сетевыми хранилищами (AWS EBS, Google Persistent Disk, Ceph, NFS).

### Живое демо

Посмотрим, как два контейнера могут общаться через общую папку в оперативной памяти ноды.

1. Создаем `ephemeral-demo.yaml`:

   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: shared-data-pod
   spec:
     containers:
       - name: writer
         image: busybox
         command:
           [
             "/bin/sh",
             "-c",
             "while true; do echo 'Data from writer' > /cache/data.txt; sleep 5; done",
           ]
         volumeMounts:
           - name: shared-storage
             mountPath: /cache
       - name: reader
         image: busybox
         command: ["/bin/sh", "-c", "tail -f /cache/data.txt"]
         volumeMounts:
           - name: shared-storage
             mountPath: /cache
     volumes:
       - name: shared-storage
         emptyDir:
           medium: Memory # Храним прямо в RAM для максимальной скорости
   ```

2. Проверка

   ```bash
   kubectl apply -f ephemeral-demo.yaml
   kubectl logs shared-data-pod -c reader
   ```

### Вопросы

- В: Что будет с данными в `emptyDir`, если контейнер внутри пода упадет и перезапустится?
  - О: Данные сохранятся, так как Pod всё еще существует.
- В: А если мы удалим сам Pod?
  - О: Данные в `emptyDir` будут безвозвратно удалены.
- В: В каких случаях `medium: Memory` может быть опасен?
  - О: Поскольку это оперативная память, она учитывается в лимитах Пода (`memory requests/limits`). Если вы запишете туда слишком много данных, ваш Под будет убит по ошибке OOMKilled.

## Блок 2: Persistent Volumes (PV) - Железо как абстракция

### Текст для выступления

В больших компаниях разработчик не должен знать, какой марки у него диск (SSD или HDD) или по какому протоколу он подключен (`NFS`, `iSCSI`). За это отвечает администратор кластера.

**Persistent Volume (PV)** - это кусок "железа", который админ уже выделил в кластере. Это ресурс, такой же как Нода. PV не принадлежит никакому неймспейсу, он общий для всего кластера.

**Ключевые особенности PV:**

1. Жизненный цикл: PV существует независимо от Подов. Если все ваши приложения удалены, PV остается на месте с вашими данными.
2. Вне неймспейсов: PV - это ресурс всего кластера (как и ноды). Он не принадлежит конкретной команде, пока его не "забронируют".
3. Типы доступа (Access Modes):
   - **ReadWriteOnce (RWO):** Диск может быть подключен только к одной ноде (как обычный HDD).
   - **ReadOnlyMany (ROX):** Много нод могут только читать (например, общая библиотека статики).
   - **ReadWriteMany (RWX):** Много нод могут писать одновременно (требует сетевых файловых систем типа `NFS` или `Ceph`).

### Живое демо

Давайте побудем в роли администратора и создадим PV вручную (статическое резервирование).

1. Создаем манифест `pv-manual.yaml`:

   ```yaml
   apiVersion: v1
   kind: PersistentVolume
   metadata:
     name: workshop-pv
   spec:
     capacity:
       storage: 5Gi # Размер диска
     volumeMode: Filesystem
     accessModes:
       - ReadWriteOnce
     persistentVolumeReclaimPolicy: Retain # Что делать с данными после удаления? (Retain - сохранить)
     storageClassName: manual # Имя класса, пригодится в следующем блоке
     hostPath:
       path: "/mnt/data" # В реальном облаке тут был бы ID диска AWS или Google
   ```

2. Создаем и проверяем статус:

   ```bash
   kubectl apply -f pv-manual.yaml

   # Посмотрим список всех дисков в кластере
   kubectl get pv
   ```

   Вы увидите статус `Available`. Это значит, что диск создан, проверен и ждет, когда какой-нибудь Под его заберет.

### Вопросы

- В: Чем `persistentVolumeReclaimPolicy`: `Retain` отличается от `Delete`?
  - О: При `Delete` физический диск в облаке удалится сразу вместе с данными, как только вы удалите запрос на него. При `Retain` диск перейдет в статус `Released`, данные останутся, но никто другой не сможет его занять, пока админ не очистит его вручную.
- В: Почему в статусе `PV` мы не видим `Namespace`?
  - О: Потому что PV - это глобальный объект кластера. Ограничение по неймспейсам появляется только на этапе "запроса" (`PVC`), который мы разберем в следующем блоке.
- В: Можно ли один PV типа `ReadWriteOnce` подключить к двум Подам на разных нодах?
  - О: Нет. Kubernetes выдаст ошибку `Multi-Attach error`. Для такой задачи нужен диск с поддержкой `ReadWriteMany`.

## Блок 3: Persistent Volume Claims (PVC) - Запрос ресурсов у кластера

### Текст для выступления

Разработчику не нужно знать имя конкретного диска `workshop-pv`, который создал админ. Вместо этого разработчик описывает свои потребности через объект **Persistent Volume Claim (PVC)**.

Это работает как сайт знакомств для данных:

1. PVC говорит: "Мне нужно 5 ГБ памяти с доступом ReadWriteOnce".
2. Kubernetes Control Plane ищет среди всех свободных PV тот, который подходит под эти параметры.
3. Как только пара найдена, происходит Binding (Связывание). Теперь этот диск забронирован под конкретный PVC и никто другой его не получит.

**Важные правила:**

- **Namespace:** В отличие от `PV`, запрос `PVC` всегда живет в конкретном неймспейсе. Вы не можете из неймспейса `prod` подключить `PVC`, который лежит в `dev`.
- **Размер:** Если вы просите 5 ГБ, а в наличии только `PV` на 10 ГБ - K8s отдаст вам его, но 5 ГБ пропадут зря. Если же вы просите 10 ГБ, а есть только по 5 ГБ - запрос будет висеть в статусе `Pending` вечно.

### Живое демо

Давайте создадим запрос, который "найдет" наш диск из предыдущего блока.

1. Создаем файл `pvc-request.yaml`:

   ```yaml
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: my-app-pvc
   spec:
     accessModes:
       - ReadWriteOnce
     resources:
       requests:
         storage: 3Gi # Мы просим 3ГБ, наш PV на 5ГБ должен подойти
     storageClassName: manual # Должен совпадать с именем в PV
   ```

2. Применяем и проверяем статус связки:

   ```yaml
   kubectl apply -f pvc-request.yaml

   # Проверяем PVC - он должен стать Bound
   kubectl get pvc

   # Проверяем PV - он тоже должен стать Bound и показать, какой PVC его занял
   kubectl get pv
   ```

3. Подключаем диск к Поду:
   Теперь мы используем имя PVC в описании Пода:

```yaml
spec:
  containers:
    - name: web-server
      image: nginx
      volumeMounts:
        - mountPath: "/usr/share/nginx/html"
          name: storage
  volumes:
    - name: storage
      persistentVolumeClaim:
        claimName: my-app-pvc
```

### Вопросы

- В: Что будет, если я удалю Под? Удалятся ли данные на диске?
  - О: Нет. `PVC` останется в статусе `Bound`, а данные - на диске. Когда вы создадите новый Под с тем же `PVC`, он увидит все старые данные.
- В: Можно ли изменить размер `PVC` "на лету"?
  - О: Зависит от драйвера хранилища. Большинство современных облачных драйверов позволяют увеличивать размер (например, с 5ГБ до 10ГБ), но уменьшать размер нельзя никогда.
- В: Что случится, если я удалю `PVC`, который сейчас используется запущенным Подом?
  - О: Удаление будет заблокировано (статус `Terminating`), пока Под не будет остановлен. Это защита от "выдергивания диска" на ходу.

## Блок 4: Storage Classes - Динамический провижининг

### Текст для выступления

В предыдущих блоках мы работали вручную: сначала создавали **PV** (диск), а потом **PVC** (заявку). В реальном облаке (`AWS`, `GCP`, `Azure`) это неудобно. Представьте, что у вас сотни разработчиков - админ сойдет с ума нарезать им диски.

Для этого существует **StorageClass (SC)**. Это "шаблон" или "автомат по выдаче дисков".

**Как работает динамический провижининг:**

1. Администратор один раз создает `StorageClass` и прописывает в нем: "Если кто-то попросит диск, иди в облако AWS, создай там `gp3` диск и подключи его".
2. Разработчик просто создает `PVC`, указывая имя этого класса.
3. Kubernetes видит запрос, обращается к облачному провайдеру, тот создает физический диск, а K8s автоматически создает `PV` и связывает его с вашим `PVC`.

Это называется **Just-in-Time** доставка ресурсов. Нет запроса - нет лишних трат на диски.

### Живое демо

Посмотрим, как выглядит описание "автомата" и как им пользоваться.

1. Описание `StorageClass` (пример для `AWS`):

   ```yaml
   apiVersion: storage.k8s.io/v1
   kind: StorageClass
   metadata:
     name: fast-ssd
   provisioner: ebs.csi.aws.com # Драйвер, который умеет общаться с облаком
   parameters:
     type: gp3
   reclaimPolicy: Delete # Удалять диск в облаке, когда удален PVC
   allowVolumeExpansion: true # Разрешить расширение диска в будущем
   ```

2. Запрос диска через этот класс:
   Файл `pvc-dynamic.yaml`:

   ```yaml
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: dynamic-pvc
   spec:
     accessModes:
       - ReadWriteOnce
     storageClassName: fast-ssd # Ссылка на наш автомат
     resources:
       requests:
         storage: 20Gi
   ```

3. Магия автоматизации:

   ```bash
   kubectl apply -f pvc-dynamic.yaml

   # Вы увидите, что PV создался САМ. Вам не нужно было писать для него YAML!
   kubectl get pvc,pv
   ```

### Вопросы

- В: Что будет, если я не укажу `storageClassName` в своем `PVC`?
  - О: Если в кластере настроен класс "по умолчанию" (`Default StorageClass`), то диск создастся через него. Если нет - `PVC` зависнет в `Pending`, - ожидая ручного создания `PV`.
- В: Можно ли с помощью `StorageClass` создавать диски не в облаке, а на своих серверах?
  - О: Да, есть решения вроде `Linstor`, `Ceph` (`Rook`) или `Longhorn`. Они превращают обычные диски ваших серверов в распределенное хранилище, работающее через StorageClass.
- В: Зачем нужен параметр `allowVolumeExpansion`?
  - О: Если он `true`, вы сможете просто поменять `20Gi` на `30Gi` в своем `PVC`, и Kubernetes сам "растянет" физический диск без потери данных.

## Блок 5: StatefulSets - Порядок и стабильность для данных

### Текст для выступления

Для обычного веб-приложения нам всё равно, как называется Pod (`web-849f...`). Но для базы данных (`PostgreSQL`, `MongoDB`, `Cassandra`) это критично. Если один узел базы упадет, он должен вернуться с тем же именем и, что самое важное, **с тем же самым диском**.

**StatefulSet (STS)** - это контроллер, созданный специально для приложений с состоянием (Stateful).

**Три кита StatefulSet:**

1. **Стабильные имена (Ordinal Index):** Поды получают имена по порядку: `db-0`, `db-1`, `db-2`. Если `db-1` умрет, новый под всегда будет называться `db-1`.
2. **Стабильные диски (VolumeClaimTemplates):** Это киллер-фича. StatefulSet сам создает PVC для каждого пода. Если db-1 переедет на другую ноду, он "примагнитит" к себе именно свой диск data-db-1.
3. **Порядок запуска и удаления:** Поды создаются строго по очереди (0, потом 1, потом 2) и удаляются в обратном порядке. Это важно для кластеров баз данных, где сначала должен подняться Master.

### Живое демо

Давайте создадим мини-кластер и посмотрим, как он управляет именами и дисками.

1. Создаем `statefulset-demo.yaml`:

   ```yaml
   apiVersion: apps/v1
   kind: StatefulSet
   metadata:
     name: database
   spec:
     serviceName: "db-service" # Нужно для сети, разберем в Блоке 6
     replicas: 3
     selector:
       matchLabels:
         app: postgres
     template:
       metadata:
         labels:
           app: postgres
       spec:
         containers:
           - name: postgres
             image: postgres:15
             volumeMounts:
               - name: data # Имя должно совпадать с шаблоном ниже
                 mountPath: /var/lib/postgresql/data
     # МАГИЯ: Шаблон, по которому STS будет сам "нарезать" диски через StorageClass
     volumeClaimTemplates:
       - metadata:
           name: data
         spec:
           accessModes: ["ReadWriteOnce"]
           storageClassName: "standard" # Твой StorageClass из Блока 4
           resources:
             requests:
               storage: 1Gi
   ```

2. Наблюдаем за порядком запуска:

   ```bash
   kubectl apply -f statefulset-demo.yaml

   # Запусти это в отдельном окне, чтобы увидеть строгую очередь (0 -> 1 -> 2)
   kubectl get pods -w
   ```

3. Проверяем диски:

   ```bash
   # Ты увидишь, что PVC создались автоматически для каждого индекса
   kubectl get pvc
   ```

### Вопросы

- В: Что будет с дисками (`PVC`), если я удалю сам `StatefulSet`?
  - О: Они останутся. Это защита Kubernetes. `STS` автоматически создает `PVC`, но никогда их автоматически не удаляет, чтобы вы случайно не стерли базу данных. Удалять диски нужно будет вручную.
- В: Можно ли масштабировать `StatefulSet` мгновенно, как `Deployment`?
  - О: Можно (через `podManagementPolicy: Parallel`), но по умолчанию он делает это по одному. Это нужно, чтобы распределенные системы (как `ElasticSearch`) успевали синхронизировать данные между узлами.
- В: Почему нельзя использовать обычный Service для обращения к `db-0`?
  - О: Обычный `Service` балансирует трафик случайно. Чтобы попасть именно на "Мастера" (`db-0`), нам нужен `Headless Service`, который мы разберем в следующем блоке.

## Блок 6: Headless Services - DNS для кластеризации

### Текст для выступления

Обычный `Service` в Kubernetes работает как балансировщик: у него есть свой IP (`ClusterIP`), и когда вы к нему стучитесь, он перекидывает вас на случайный Под. Для базы данных (например, `MongoDB` или `PostgreSQL`) это не подходит. Мастеру нужно знать точный адрес Реплики, а Реплике - точный адрес Мастера.

Для этого используется `Headless Service`.

В чем отличия:

1. **Нет IP-адреса:** В манифесте мы пишем `clusterIP`: None. У сервиса нет собственного виртуального IP.
2. **Прямой DNS:** Вместо одного IP сервис возвращает через DNS список IP-адресов всех Подов, которые за ним стоят.
3. **Предсказуемые имена:** В связке со `StatefulSet` это дает нам магию. Каждый Под получает уникальное доменное имя, которое не меняется: `<имя-пода>.<имя-сервиса>.<namespace>.svc.cluster.local`

Например: `db-0.db-service.default.svc.cluster.local` всегда будет вести именно на 0-й индекс вашего `StatefulSet`.

### Живое демо

Давайте создадим "адресную книгу" для нашего кластера БД и проверим, как работает DNS.

1. Создаем манифест `headless-service.yaml`:

   ```yaml
   apiVersion: v1
   kind: Service
   metadata:
     name: db-service # Это имя должно совпадать с serviceName в StatefulSet
   spec:
     # МАГИЯ: Делаем сервис "безголовым"
     clusterIP: None
     selector:
       app: postgres
     ports:
       - protocol: TCP
         port: 5432
         targetPort: 5432
   ```

   ```bash
   kubectl apply -f headless-service.yaml

   # Запускаем проверочный под
   kubectl run dns-test --image=busybox:1.28 --restart=Never -- sleep 3600

   # Делаем запрос к нашему сервису
   kubectl exec dns-test -- nslookup db-service
   ```

   В ответе вы увидите не один IP, а список IP всех запущенных реплик вашего `StatefulSet`.

2. Проверяем конкретный под:

   ```bash
   kubectl exec dns-test -- nslookup database-0.db-service
   Это вернет IP конкретно первого пода.
   ```

### Вопросы

- В: Почему нельзя просто использовать IP-адреса подов напрямую?
  - О: IP подов меняются при каждом рестарте. DNS-имя `database-0.db-service` остается неизменным, даже если под переехал на другую ноду и получил новый IP.
- В: Зачем в `StatefulSet` поле `serviceName`?
  - О: Оно связывает поды с конкретным `Headless-сервисом`. Без этого поля Kubernetes не сможет создать стабильные DNS-записи для каждого индекса.
- В: Может ли клиентское приложение использовать `Headless Service`?
  - О: Обычно нет. Приложение хочет один адрес, который "просто работает" (балансировщик). `Headless Service` нужен для внутренней кухни кластерных приложений (чтобы база данных собралась в кластер).

## Блок 7: Volume Snapshots - Машина времени для данных

### Текст для выступления

Раньше для бэкапа базы данных нам приходилось запускать `pg_dump` или копировать файлы вручную. Это долго и нагружает систему. В современном Kubernetes есть стандарт **CSI (Container Storage Interface)**, который позволяет давать команду напрямую облаку (`AWS`, `GCP`) или хранилищу (`Ceph`): "Сделай снимок этого диска прямо сейчас".

**Volume Snapshots** работают в два этапа:

1. **VolumeSnapshotClass:** Шаблон, который говорит, какой драйвер использовать для создания снимка (например, `ebs.csi.aws.com`).
2. **VolumeSnapshot:** Сам объект-запрос. Это как фотография вашего диска в определенный момент времени.

**Почему это круто?**

- **Мгновенно:** Создание снимка в облаке происходит почти моментально (через механизм `Copy-on-Write`).
- **Восстановление:** Вы можете создать новый `PVC` (диск) не "пустым", а указав этот Snapshot как источник.
- **Независимость:** Даже если вы случайно удалите `PVC`, Snapshot останется (в зависимости от настроек).

### Живое демо

Посмотрим, как "заморозить" состояние данных.

1. Создаем `SnapshotClass` (подготовлено админом):

   ```yaml
   apiVersion: snapshot.storage.k8s.io/v1
   kind: VolumeSnapshotClass
   metadata:
     name: csi-aws-vsc
   driver: ebs.csi.aws.com
   deletionPolicy: Delete # Снимок в облаке удалится, если удалить объект в K8s
   ```

2. Делаем снимок нашего рабочего диска:

   ```yaml
   apiVersion: snapshot.storage.k8s.io/v1
   kind: VolumeSnapshot
   metadata:
     name: db-backup-snapshot
   spec:
     volumeSnapshotClassName: csi-aws-vsc
     source:
       persistentVolumeClaimName: data-database-0 # Имя PVC нашего StatefulSet
   ```

3. Проверяем статус:

   ```bash
   kubectl apply -f snapshot.yaml

   # Ждем, пока READYTOUSE станет true
   kubectl get volumesnapshot
   ```

4. Как восстановиться?

   Просто создаем новый `PVC`, указав `Snapshot` в `dataSource`:

   ```yaml
   spec:
     dataSource:
       name: db-backup-snapshot
       kind: VolumeSnapshot
       apiGroup: snapshot.storage.k8s.io
     resources:
       requests:
         storage: 1Gi # Размер должен быть не меньше оригинала
   ```

### Вопросы

- В: Нужно ли останавливать базу данных перед созданием `Snapshot`?
  - О: В идеале - да (сделать `FLUSH TABLES WITH READ LOCK` или аналоги), чтобы данные на диске были консистентны. Но современные файловые системы и БД обычно переживают "холодный" снимок, просто запуская процедуру восстановления из логов при старте.
- В: Является ли Snapshot полноценным бэкапом?
  - О: Не совсем. Снимок часто хранится в той же корзине/инфраструктуре, что и диск. Если упадет весь регион облака или вы случайно удалите весь аккаунт, снимки могут пропасть. Настоящий бэкап подразумевает копирование данных в другое место (например, `S3`).
- В: Можно ли сделать `Snapshot` из `PVC`, который сейчас подключен к работающему Поду?
  - О: Да, это стандартный сценарий. Драйвер сделает снимок "на лету".

## Блок 8: Jobs - Разовые задачи и миграции

### Текст для выступления

В Kubernetes есть тип задач, которые не должны перезапускаться бесконечно. Например:

1. **Миграции БД:** Нужно один раз обновить структуру таблиц перед запуском новой версии приложения.
2. **Обработка данных:** Взять тяжелый файл, сконвертировать его и положить результат в хранилище.
3. **Разовая настройка:** Создать пользователя в стороннем сервисе или прогреть кэш.

Для этого используется объект Job.

**В чем отличие от обычного Пода:**

- Если процесс внутри Пода завершается с кодом `0` (Success), `Job` считает задачу выполненной и больше не перезапускает контейнер.
- Если процесс упал с ошибкой, `Job` будет пробовать перезапустить его столько раз, сколько указано в параметре `backoffLimit`.
- Когда задача выполнена, Под остается в системе в статусе `Completed`, чтобы вы могли зайти и посмотреть логи.

### Живое демо

Давайте запустим задачу, которая имитирует миграцию базы данных.

1. Создаем манифест `migration-job.yaml`:

   ```yaml
   apiVersion: batch/v1
   kind: Job
   metadata:
     name: db-migration
   spec:
     # Сколько раз пытаться перезапустить при ошибке
     backoffLimit: 4
     # Время жизни завершенного пода (чтобы не чистить руками)
     ttlSecondsAfterFinished: 100
     template:
       spec:
         containers:
           - name: migration
             image: postgres:15
             command:
               [
                 "/bin/sh",
                 "-c",
                 "echo 'Running migrations...'; sleep 5; echo 'Success!'",
               ]
         # Важно: для Job допустимы только OnFailure или Never
         restartPolicy: OnFailure
   ```

2. Запускаем и следим за статусом:

   ```yaml
   kubectl apply -f migration-job.yaml

   # Видим, как под переходит в статус Completed
   kubectl get pods

   # Проверяем отчет самого объекта Job
   kubectl get jobs
   ```

### Вопросы

- В: Что будет, если задача "зависнет" (например, бесконечный цикл)?
  - О: Для этого есть параметр `activeDeadlineSeconds`. По истечении этого времени Kubernetes принудительно убьет задачу и пометит её как `Failed`.
- В: Почему нельзя запускать миграции внутри Init-контейнеров обычного Deployment?
  - О: Можно, но это опасно. Если у вас 10 реплик приложения, они все одновременно попытаются запустить одну и ту же миграцию. `Job` же гарантирует контролируемый запуск.
- В: Как запустить `Job` заново?
  - О: Объекты `Job` нельзя просто "перезапустить". Нужно удалить старый (`kubectl delete job ...`) и создать новый, либо использовать другое имя.

## Блок 9: CronJobs - Планировщик задач

### Текст для выступления

Если **Job** - это разовый приказ ("Сделай это сейчас"), то **CronJob** - это расписание ("Делай это каждый вторник в 3 часа ночи").

Это стандартный механизм автоматизации в Kubernetes, который работает поверх обычных **Jobs**. Мы используем его для:

1. **Бэкапов:** Раз в сутки делать дамп базы данных и отправлять его в **S3**.
2. **Очистки:** Раз в неделю удалять старые логи или временные файлы из хранилища.
3. **Отчетов:** Каждое утро собирать статистику и отправлять её в Telegram/Slack.

Синтаксис расписания здесь классический как в **Linux Cron** (пять звездочек: минуты, часы, дни, месяцы, дни недели).

### Живое демо

Создадим задачу, которая будет "делать бэкап" каждую минуту.

1. Создаем файл `backup-cronjob.yaml`:

   ```yaml
   apiVersion: batch/v1
   kind: CronJob
   metadata:
     name: daily-db-backup
   spec:
     # Расписание: раз в минуту (для теста)
     schedule: "*/1 * * * *"
     # Что делать, если старая задача еще не закончена (Allow, Forbid, Replace)
     concurrencyPolicy: Forbid
     jobTemplate:
       spec:
         template:
           spec:
             containers:
               - name: backup-worker
                 image: postgres:15
                 command:
                   [
                     "/bin/sh",
                     "-c",
                     "echo 'Backup started...'; sleep 10; echo 'Backup uploaded to S3'",
                   ]
             restartPolicy: OnFailure
   ```

2. Наблюдаем за выполнением:

   ```bash
   kubectl apply -f backup-cronjob.yaml

   # Список всех расписаний
   kubectl get cronjobs

   # Ждем минуту и видим, как создаются Jobs, а из них - Поды
   kubectl get jobs --watch
   ```

### Вопросы

- В: Что будет, если задача должна запуститься, а предыдущая еще не завершилась?
  - О: Это регулирует `concurrencyPolicy`. `Allow` (по умолчанию) запустит вторую параллельно. `Forbid` пропустит запуск, пока старая не закончит. Replace убьет старую и запустит новую. Для бэкапов лучше всего использовать `Forbid`.
- В: Нужно ли удалять старые поды от `CronJob` вручную?
  - О: Нет. Есть параметры `successfulJobsHistoryLimit` (по умолчанию 3) и `failedJobsHistoryLimit` (по умолчанию 1). Kubernetes сам будет хранить историю только за последние несколько запусков.
- В: Как запустить `CronJob` немедленно, не дожидаясь времени по расписанию?
  - О: Можно создать `Job` "на основе" `CronJob` вручную:
    `kubectl create job --from=cronjob/daily-db-backup manual-run-01`

## Блок 10: Backup Strategies & Velero - План спасения

### Текст для выступления

Снапшоты (Блок 7) - это круто, но это не бэкап. Если вы случайно удалите весь проект в облаке или кластер будет взломан, снапшоты могут исчезнуть вместе с ним. Настоящая стратегия бэкапа должна отвечать на вопрос: "Как мне поднять всё с нуля в другом регионе или у другого провайдера?"

Для этого в мире Kubernetes есть стандарт де-факто - **Velero**.

**Что делает Velero:**

1. **Бэкап метаданных:** Сохраняет все ваши YAML-конфиги (`Deployments`, `Secrets`, `ConfigMaps`) в объектное хранилище (например, **S3**).
2. **Бэкап данных:** Дает команду на создание снапшотов дисков или копирует данные напрямую из файловой системы (через инструмент `Restic/Kopia`).
3. **Восстановление (Restore):** Вы разворачиваете чистый кластер, ставите **Velero**, указываете на ту же корзину **S3**, и он магическим образом воссоздает все ресурсы и подключает диски.

#### Подходы к Disaster Recovery (DR)

1. **Backup & Restore (Самый дешевый):** У вас есть бэкапы. Если кластер умер, вы поднимаете новый и восстанавливаетесь. Время простоя (**RTO**) - часы.
2. **Pilot Light:** В другом регионе стоит минимальный "скелет" кластера. При аварии вы быстро масштабируете его и переключаете трафик. Время простоя - десятки минут.
3. **Multi-Region / Active-Active (Самый дорогой):** Два кластера работают одновременно. Если один падает, пользователи даже не замечают.

### Живое демо (Обзор команд)

**Velero** - это CLI-инструмент. Вот как выглядят типичные операции:

1. Создание бэкапа всего кластера:

   ```bash
   velero backup create full-cluster-backup --include-namespaces '*'
   ```

2. Бэкап только базы данных по расписанию внутри Velero:

   ```bash
   velero schedule create daily-db-backup --schedule="0 1 * * *" --include-namespaces database
   ```

3. Момент истины - восстановление в новом кластере:

   ```bash
   velero restore create --from-backup full-cluster-backup
   ```

### Вопросы

- В: Почему нельзя просто хранить все YAML-файлы в Git (`GitOps`) вместо бэкапа метаданных?
  - О: **GitOps** - это отлично, но он не хранит состояние (например, секреты, созданные вручную, или динамические сертификаты). `Velero` делает "слепок" того, что реально работает в кластере прямо сейчас.
- В: Можно ли с помощью `Velero` переехать из `Google Cloud` в `AWS`?
  - О: Да, если использовать плагин `Restic`. Он копирует данные на уровне файлов, поэтому ему неважно, какие диски используются "под капотом" у провайдеров.
- В: Как часто нужно проверять бэкапы?
  - О: Бэкап, который не проверяли на восстановление, считается отсутствующим. Хорошая практика - раз в месяц проводить учения по восстановлению (Game Day).
