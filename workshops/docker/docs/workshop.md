## Блок 1: Архитектура и Движок

Docker произвел революцию, потому что он решил проблему «на моей машине всё работает». Но важно понимать: контейнер — это НЕ виртуальная машина. У него нет своего ядра. Он использует ядро хостовой системы.
Изоляция достигается двумя фишками ядра Linux:

1. **Namespaces (Пространства имен):** контейнер думает, что он один в системе (свои процессы, сеть, пользователи).
2. **Control Groups (Cgroups):** лимиты ресурсов. Чтобы один контейнер не "съел" всю оперативку сервера.

### Живое демо

```bash
# Посмотрим процессы на хосте
ps aux | wc -l

# Запустим контейнер и посмотрим процессы внутри
docker run --rm alpine ps aux
```

_Заметим, что внутри контейнера PID 1 — это сама запущенная команда._

2. Демонстрация общей памяти ядра:

```bash
# Узнаем версию ядра на хосте
uname -r

# Узнаем версию ядра внутри любого контейнера
docker run --rm debian uname -r
```

_Они идентичны. Это доказывает, что ядро общее._

### Выводы

- Контейнер — это просто изолированный процесс.
- Быстрее ВМ, так как не тратит ресурсы на загрузку гостевой ОС.
- Docker использует Linux-специфичные технологии (Namespaces, Cgroups).

### Вопросы

- В: Что произойдет, если в контейнере упадет ядро (Kernel Panic)?
  - О: Упадет весь сервер (хост), так как ядро общее.
- В: Контейнеры безопаснее виртуальных машин?
  - О: Обычно менее безопасны из-за меньшего слоя изоляции (общее ядро), поэтому важна настройка прав.

## Блок 2: Манипуляции с контейнерами

### Текст для выступления

Запуск контейнера — это база. Мы можем запускать их в интерактивном режиме (чтобы посидеть внутри) или в фоновом (как демоны). Главное правило Docker: контейнер живет до тех пор, пока живет его основной процесс (PID 1). Как только процесс завершился — контейнер переходит в статус Exited.

### Живое демо

1. Интерактив

```bash
docker run -it --name my_bash ubuntu bash
# Внутри можно погулять, создать файлы. После exit контейнер спит.
```

2. Фоновый режим:

```bash
docker run -d --name web_server nginx
```

3. Инспекция:

```bash
# Посмотреть логи фонового контейнера
docker logs web_server

# Зайти в уже запущенный контейнер (Магия exec)
docker exec -it web_server bash
```

### Выводы

- `-it` — для работы руками.
- `-d` — для серверов/сервисов.
- `--rm` — для одноразовых задач.
- `docker ps -a` — показывает вообще всё, что вы когда-либо запускали.

### Вопросы

- В: В чем разница между `docker stop` и `docker kill`?
  - О: `stop` посылает `SIGTERM` (вежливая просьба завершиться), `kill` — `SIGKILL` (рубит мгновенно).
- В: Как вытащить файл из контейнера на хост?
  - О: Команда `docker cp <container_id>:/path/to/file ./local_path.`

## Блок 3: Сети и Порты — Как не потеряться в изоляции

### Текст для выступления

Контейнер изолирован по сети (Network Namespace). У него свой IP-адрес, своя таблица маршрутизации и свой `localhost`.

Представьте: вы запустили веб-сервер внутри контейнера на порту 80. Если вы просто введете в браузере `http://localhost`, вы ничего не увидите. Почему? Потому что ваш браузер ищет порт 80 на вашем ноутбуке, а сервер сидит в "коробке". Чтобы магия сработала, мы используем Publishing (проброс портов). Мы буквально говорим Docker: "Любой трафик, пришедший на порт 8080 моего ноутбука, перенаправляй в порт 80 этого контейнера".

Но есть и вторая проблема: общение контейнеров между собой. Если ваше приложение хочет подключиться к базе данных в соседнем контейнере, оно не может использовать `localhost`. Для этого существуют **Docker Networks**, где контейнеры видят друг друга по именам, как в настоящей локальной сети.

### Живое демо

1. **Проброс портов (Mapping).** Запустим веб-сервер и свяжем порты.

```bash
# Запускаем nginx. Порт 8080 на хосте -> порт 80 внутри контейнера
docker run -d --name web-test -p 8080:80 nginx

# Проверяем в браузере или через curl
curl http://localhost:8080
```

2. **Ловушка localhost.** Попробуем доказать, что внутри контейнера всё иначе.

```bash
# Зайдем внутрь контейнера и попробуем достучаться до порта 8080
docker exec -it web-test curl http://localhost:8080
# ОШИБКА! Внутри контейнера на 8080 никто не слушает. Там слушают на 80.
```

3. **Своя сеть (User-defined Bridge).** Создадим сеть и заставим контейнеры дружить.

```bash
# Создаем сеть
docker network create my-app-net

# Запускаем "базу данных" (просто alpine с портом) в этой сети
docker run -d --name database --network my-app-net alpine sleep 1000

# Запускаем "приложение" в той же сети и пингуем базу по ИМЕНИ
docker run --rm --network my-app-net alpine ping -c 2 database
```

_Интересный факт: В дефолтной сети bridge резолвинг имен не работает. Только в созданных пользователем!_

4. **Как достучаться до хоста?** Иногда приложению в контейнере нужно подключиться к БД, которая запущена прямо на твоем Mac или Linux.

```bash
# Специальный DNS-адрес для обращения из контейнера к хосту
docker run --rm alpine ping -c 1 host.docker.internal
```

### Выводы

- `-p [хост_порт]:[контейнер_порт]` — открывает дверь из внешнего мира внутрь.
- `localhost` внутри контейнера — это петля на самого себя. Для связи с другими используй имена контейнеров.
- `Docker Network` — создает виртуальный свитч. Контейнеры в одной сети видят все порты друг друга (даже если они не проброшены через -p).
- Биндинг на IP: `127.0.0.1:8080:80` безопаснее, чем `8080:80`, так как не открывает порт для всей вашей Wi-Fi сети.

### Вопросы

- В: Будет ли работать связь по именам, если я не создал свою сеть, а просто запустил два контейнера через `docker run`?
  - О: Нет. В стандартной сети `bridge` (которая идет по умолчанию) контейнеры могут общаться только по IP-адресам. DNS-сервер Docker включается только в пользовательских сетях.
- В: В чем разница между `--net host` и обычным пробросом портов?
  - О: В режиме `host` контейнер полностью лишается сетевой изоляции и использует порты хоста напрямую. Это быстрее, но небезопасно и может вызвать конфликты портов.
- В: Что такое флаг `--expose`?
  - О: Это просто документация. Он не открывает порты наружу, а лишь подсказывает другим инструментам, на каких портах ожидать трафик. Реальную работу делает только `-p`.

## Блок 4: Volumes — Где живут данные, когда контейнер умирает?

### Текст для выступления

Контейнеры по своей природе — это расходный материал. Если вы запишете данные внутрь работающего контейнера и удалите его — ваши данные улетят в цифровую черную дыру. Это называется **Ephemeral Storage**.

Чтобы базы данных и логи выживали, Docker предлагает два основных пути:

1. **Bind Mounts:** Вы буквально привязываете папку со своего ноутбука к папке внутри контейнера. Изменили код в VS Code — он тут же изменился в контейнере. Это наш основной инструмент для разработки.
2. **Named Volumes:** Это изолированные области, которыми управляет сам Docker. Вы не лезете туда руками через проводник, но Docker гарантирует, что данные сохранятся, даже если вы пересоздадите контейнер. Они быстрее и безопаснее для баз данных.

Главное правило: **Никогда не храните важные данные внутри записываемого слоя контейнера. Используйте вольюмы.**

### Живое демо

1. Трагедия потери данных.

```bash
# Создаем файл внутри контейнера
docker run --name temporary alpine sh -c "echo 'Важные данные' > /data.txt"

# Удаляем контейнер
docker rm temporary

# Пытаемся найти файл (спойлер: его нет)
docker run --rm alpine ls /data.txt
```

2. Named Volumes (Для баз данных).

```bash
# Создаем именованный вольюм
docker volume create my_db_data

# Запускаем контейнер и монтируем вольюм в /data
docker run -d --name db_server -v my_db_data:/data alpine sleep 1000

# Пишем данные
docker exec db_server sh -c "echo 'Я выживу!' > /data/save.txt"

# Пересоздаем контейнер
docker rm -f db_server
docker run --rm -v my_db_data:/data alpine cat /data/save.txt
```

3. Bind Mounts (Для разработки).

```bash
# Создаем папку на хосте
mkdir ./html
echo "<h1>Hello from Host</h1>" > ./html/index.html

# Монтируем ТЕКУЩУЮ папку в nginx (используем $(pwd) для полного пути)
docker run -d -p 8081:80 -v "$(pwd)/html:/usr/share/nginx/html" nginx

# Теперь измените файл в папке ./html на хосте и обновите страницу в браузере!
```

4. Инспекция вольюмов.

```bash
# Посмотрим, где Docker на самом деле прячет Named Volumes
docker volume inspect my_db_data
# (На Linux это обычно /var/lib/docker/volumes/...)
```

### Выводы

- **Named Volumes (`-v name:/path`):** Управляются Docker. Лучший выбор для БД и постоянного хранения.
- **Bind Mounts (`-v /host/path:/container/path`):** Прямая связь с файловой системой хоста. Идеально для проброса кода или конфигов.
- **Read-Only монтирование:** Можно добавить `:ro` в конце (например, `-v /conf:/app/conf:ro`), чтобы контейнер не мог случайно испортить ваши конфиги.
- **Производительность:** Вольюмы работают быстрее, чем слои контейнера, так как обходят механизм Copy-on-Write.

### Вопросы

- В: Что будет, если я примонтирую пустую папку с хоста (Bind Mount) в папку контейнера, где уже были файлы (например, `/etc`)?
  - О: Папка в контейнере станет пустой. Файлы хоста «перекроют» содержимое контейнера. Будьте осторожны!
- В: Как перенести Named Volume на другой сервер?
  - О: Напрямую — никак (это просто папка). Нужно запустить временный контейнер, сделать tar архив содержимого вольюма и развернуть его на новом месте.
- В: В чем разница между флагами `-v` и `--mount`?
  - О: `-v` — старый и лаконичный. `--mount` — новый, более подробный и понятный. Docker рекомендует использовать `--mount` в Swarm и для явности, но `-v` остается самым популярным в быту.

## Блок 5: Environment Variables — Конфигурация без границ

### Текст для выступления

Представьте, что ваше приложение должно подключаться к базе данных. На вашем ноутбуке адрес базы `localhost`, а на сервере — `db.prod.company.com`. Неужели нам нужно собирать два разных образа? Конечно, нет.

Мы используем переменные окружения (Environment Variables). Это динамические значения, которые мы впрыскиваем внутрь контейнера в момент его запуска. Образ остается неизменным («золотым»), а поведение приложения меняется в зависимости от того, что мы передали на старте.

Мы разберем два способа: флаг `-e` для быстрых тестов и `.env` файлы для серьезной работы, чтобы не захламлять терминал длинными командами

### Живое демо

1. Базовая передача через -e.

```bash
# Используем стандартный образ alpine и выведем переменную внутри
docker run --rm -e APP_COLOR=red alpine printenv APP_COLOR
```

2. Конфигурация готовых образов (на примере MariaDB/MySQL).

_Многие официальные образы требуют переменные для инициализации._

```bash
# Запускаем БД, передав пароль root через переменную
docker run -d --name my-db -e MARIADB_ROOT_PASSWORD=secret_pass mariadb

# Проверим, что пароль принят (заходим внутрь)
docker exec -it my-db mariadb -u root -psecret_pass -e "SELECT 'YES' as authenticated;"
```

3. Работа с `.env` файлами.

_Когда переменных много, флаги -e становятся нечитаемыми._

```bash
# Создаем файл с конфигами
echo "DB_USER=admin" > config.env
echo "DB_PASS=super_secret" >> config.env
echo "DEBUG=true" >> config.env

# Запускаем контейнер, подтягивая весь файл целиком
docker run --rm --env-file config.env alpine printenv | grep -E "DB_|DEBUG"
```

4. Просмотр переменных в запущенном контейнере.

```bash
# Если вы забыли, с какими параметрами запущен сервис
docker inspect my-db --format '{{range .Config.Env}}{{println .}}{{end}}'
```

- **Разделяй код и конфиг.** Образ — это код, переменные окружения — это конфиг.
- **Флаг `-e`** — для разовых запусков и тестов.
- **Флаг `--env-file`** — для удобного управления группами настроек.
- **Безопасность.** Избегайте хранения секретов в Dockerfile. Используйте `.env` файлы (и добавляйте их в `.gitignore`!).

_Если переменная задана и в `.env` файле, и через флаг `-e` в командной строке, то `-e` победит. Это позволяет переопределять дефолтные настройки на лету._

### Вопросы

- В: Видны ли переменные окружения другим пользователям на сервере?
  - О: Да, любой, кто может запустить `docker inspect`, увидит их значения. Для по-настоящему чувствительных данных (сертификаты, ключи) в Docker Swarm или Kubernetes используют специальные механизмы `Secrets`.
- В: Как передать переменную из моей текущей командной строки (shell) внутрь контейнера?
  - О: Если переменная уже есть в вашей системе (например, `export API_KEY=123`), вы можете просто написать `docker run -e API_KEY` ... без знака `=`, и Docker сам подтянет значение из хоста.
- В: Можно ли изменить переменную окружения в уже запущенном контейнере?
  - О: Нет. Переменные окружения задаются при старте процесса. Чтобы их изменить, контейнер нужно остановить и запустить заново с новыми параметрами.

## Блок 6: Dockerfile — Рецепт вашего приложения

### Введение

- Главная ошибка новичков: Путаница между `RUN` и `CMD`. Объясни: `RUN` выполняется в процессе сборки (один раз, создавая слой), а `CMD` выполняется в момент запуска контейнера.
- Если использовать `CMD ["node", "app.js"]` (exec form), процесс получит `SIGTERM` при остановке. Если использовать `CMD node app.js` (shell form), процесс запустится внутри `/bin/sh -c`, и сигналы до него не дойдут, что приведет к «зависанию» контейнера на 10 секунд при стопе.

### Текст для выступления

Dockerfile — это обычный текстовый файл, который автоматизирует создание образа. Вместо того чтобы заходить в контейнер и руками устанавливать пакеты, мы записываем шаги один раз.

Основные команды, которые нам нужны:

- **FROM:** Всегда первая строка. Мы не строим ОС с нуля, мы берем готовый фундамент (Ubuntu, Python, Alpine).
- **RUN:** Команды, которые меняют файловую систему (установка софта, создание папок). Каждый `RUN` — это новый неизменяемый слой.
- **COPY:** Перенос файлов с вашего компьютера внутрь образа.
- **CMD:** Самое важное. Это команда "по умолчанию", которая запустится, когда кто-то напишет `docker run`. В Dockerfile может быть только одна CMD.

### Живое демо

1. **Пишем первый Dockerfile.** Создадим простое веб-приложение на Python.

```bash
# Создадим рабочую папку
mkdir my-python-app && cd my-python-app

# Создадим простейший скрипт app.py
echo "print('Hello from Dockerized Python!')" > app.py

# Создаем Dockerfile
cat <<EOF > Dockerfile
FROM python:3.9-slim
WORKDIR /app
COPY app.py .
CMD ["python", "app.py"]
EOF
```

2. **Процесс сборки (Build).**

```bash
# Собираем образ и даем ему имя (тег)
docker build -t my-first-app .
```

_Обратите внимание на шаги Step 1/4... Это Docker проходит по вашим инструкциям._

3. Запуск результата.

```bash
docker run --rm my-first-app
```

4. **Эксперимент с RUN.** Добавим установку утилиты, чтобы увидеть создание слоя.

```bash
# Обновим Dockerfile (добавь это перед COPY)
RUN apt-get update && apt-get install -y curl
```

_Повтори сборку. Видишь, как Docker переиспользует кеш для первых строк и собирает только новые?_

### Выводы

- **Dockerfile читается сверху вниз.**
- **Кеширование:** Docker запоминает результат каждой строки. Если строка не изменилась, он берет её из кеша.
- **WORKDIR:** Всегда используйте эту инструкцию вместо `cd` внутри Dockerfile, чтобы явно задать рабочую папку.
- **CMD vs ENTRYPOINT:** `CMD` легко переопределить при запуске (`docker run image command`), а `ENTRYPOINT` — это "жесткая" команда, к которой аргументы просто дописываются.

### Вопросы

- В: В чем разница между `COPY` и `ADD`?
  - О: `COPY` просто копирует файлы. `ADD` умеет чуть больше: скачивать файлы по URL и автоматически распаковывать архивы `.tar.gz`. Рекомендуется всегда использовать `COPY`, если вам не нужна магия с архивами.
- В: Почему мой образ весит 1 ГБ, хотя мой скрипт всего 10 строк?
  - О: Скорее всего, вы выбрали тяжелый базовый образ (например, `FROM python:latest`). Попробуйте `-slim` или `-alpine` версии, они значительно легче.
- В: Можно ли запустить несколько приложений в одном контейнере через несколько `CMD`?
  - О: Нет. Сработает только последняя инструкция `CMD`. Docker придерживается философии "один процесс — один контейнер". Если нужно запустить сразу несколько сервисов, используйте Docker Compose.

Готовы оптимизировать этот процесс? Блок 7 посвящен тому, как сделать эти слои максимально эффективными и быстрыми.

## Блок 7: Оптимизация Dockerfile — Слоеная пицца и магия кеша

### Введение

- **Эффект домино:** Помните, я говорил, что Docker кеширует каждый шаг, но тут важно знать, что если ты изменил одну строку (например, `COPY . .`), то все последующие шаги кеш теряют и пересобираются заново.
- **Слоеная пицца:** Аналогия со слоями. Если ты решил поменять соус (нижний слой), тебе придется пересобрать всю начинку сверху. Поэтому «тяжелые» и редко меняющиеся слои (установка зависимостей) кладем вниз, а «легкий» код — наверх.

_Есть такая крутая штука как **BuildKit**. Это современный движок сборки, который умеет собирать независимые слои параллельно. Включить его можно переменной `DOCKER_BUILDKIT=1`._

### Текст для выступления

Написать Dockerfile легко, но написать его правильно — это искусство. Плохой Dockerfile заставляет вас ждать сборку по 10 минут каждый раз, когда вы поменяли одну запятую в коде.

Мы будем бороться за две вещи:

1. **Скорость сборки (Cache Layers):** Правильный порядок команд позволяет Docker переиспользовать 90% работы из предыдущих попыток.
2. **Размер образа:** Лишние мегабайты — это медленный деплой и лишние деньги за хранение. Мы научимся удалять мусор сразу после использования и выбирать правильные базовые образы».

### Живое демо

1. Демонстрация «убийства» кеша.

_Сейчас посмотрим, как неправильный порядок замедляет нас._

```bash
mkdir optimize-test && cd optimize-test
touch app.py requirements.txt

# ПЛОХОЙ ПРИМЕР: сначала копируем всё, потом ставим зависимости
cat <<EOF > Dockerfile.bad
FROM python:3.9-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
EOF
```

Соберем (первый раз долго)

```bash
docker build -t bad-cache -f Dockerfile.bad .
```

Теперь изменим `app.py` (просто добавим пробел) и соберем снова. Docker пересоберет RUN pip install заново! Это потеря времени.

2. Правильный порядок (Сначала зависимости).

```bash
cat <<EOF > Dockerfile.good
FROM python:3.9-slim
WORKDIR /app

# Копируем ТОЛЬКО файл со списком библиотек
COPY requirements.txt .
RUN pip install -r requirements.txt
# И только в самом конце копируем код
COPY . .
CMD ["python", "app.py"]
EOF
```

_Соберите это дважды, меняя app.py. Вы увидите "Using cache" на этапе установки библиотек!_

3. Уменьшение размера: цепочки RUN.

```bash
# Вместо трех RUN:
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# Делаем один (профи-стайл):
RUN apt-get update && apt-get install -y \
    curl \
 && rm -rf /var/lib/apt/lists/*
```

_Интересный факт: Если удалить временные файлы в другом RUN, они останутся в предыдущем слое и образ не похудеет._

4. Выбор базы: Alpine vs Slim.

```bash
# Сравним размеры в терминале
docker pull python:3.9
docker pull python:3.9-slim
docker pull python:3.9-alpine
docker images | grep python
```

### Выводы

- Меняющееся — вниз, стабильное — вверх. Код приложения должен копироваться последним.
- Объединяй логически связанные команды. `apt-get update` и `install` всегда должны быть в одном `RUN`.
- Чисти за собой в том же слое. Удалил кэши пакетного менеджера в том же RUN, где установил софт — сэкономил место.
- Используй `.dockerignore`. Не давай Docker копировать папку .`git`, логи и временные файлы внутрь образа.

### Вопросы

Вопросы

- В: Почему бы всегда не использовать Alpine, раз он самый маленький?
  - О: Alpine использует библиотеку `musl` вместо стандартной `glibc`. Некоторые сложные библиотеки (особенно на Python или С++) могут работать медленнее или вообще не собраться без танцев с бубном. `slim` — часто золотая середина.
- В: Можно ли как-то "схлопнуть" (squash) все слои в один?
  - О: Да, есть флаг `--squash` при сборке, но это убивает преимущество переиспользования слоев между разными образами. Лучше использовать Multi-stage сборку (наш следующий блок!).
- В: Влияет ли количество пробелов или комментариев в Dockerfile на размер образа?
  - О: Нет. Dockerfile — это текстовая инструкция. На размер влияют только файлы, которые попали в слои в результате команд `RUN`, `COPY` или `ADD`.

## Блок 8: Multi-stage Builds — Диета для ваших образов

### Введение

- Для сборки приложения (например, на Go, Java или Node.js) нам нужны компиляторы, пакетные менеджеры, кэши и исходники. Но для запуска готового бинарника или статики всё это — балласт и дыра в безопасности.
- Образ `scratch`. Это абсолютно пустой образ (0 байт). Если ваше приложение скомпилировано статически (как на Go), его можно положить в `scratch`, получив максимально защищенный образ, где нет даже `sh` или `ls` для взломщика.

### Текст для выступления

Раньше разработчики использовали "Builder pattern": один Dockerfile для сборки, скрипт для копирования артефакта на хост, и второй Dockerfile для финального образа. Это было больно и неудобно.

**Multi-stage Builds** позволяют описать весь этот процесс в одном файле. Мы используем несколько инструкций `FROM`.

- Первый этап (stage) — это мастерская. Там грязно, много инструментов и тяжелых зависимостей.
- Второй этап — это чистая комната. Мы просто забираем готовый результат (бинарный файл или билд фронтенда) из первого этапа и кладем его в крошечный базовый образ.

Результат: образ худеет с 800 МБ до 15-20 МБ за один запуск

### Живое демо

1. Создаем приложение на Go (или любой компилируемый язык).

Go идеально подходит для примера, так как на выходе дает один файл.

```bash
mkdir multi-stage-test && cd multi-stage-test
# Создаем простейший main.go
cat <<EOF > main.go
package main

import "fmt"

func main() {
  fmt.Println("Я МАЛЕНЬКИЙ ПРОД РЕДИ КОД!")
}
```

2. Пишем Multi-stage Dockerfile.

```Dockerfile
# ЭТАП 1: Сборка (называем его AS builder)
FROM golang:1.21-alpine AS builder
WORKDIR /build
COPY main.go .
RUN go build -o myapp main.go

# ЭТАП 2: Финальный образ
FROM alpine:latest
WORKDIR /app
# Магия: копируем файл ИЗ другого этапа
COPY --from=builder /build/myapp .

CMD ["./myapp"]
```

3. Сравниваем размеры.

```bash
# Собираем наш шедевр
docker build -t tiny-app .

# Смотрим разницу с официальным образом Go
docker images | grep -E "tiny-app|golang"
```

_Вы увидите, что `golang` весит около 300МБ+, а ваш `tiny-app` — около 12МБ._

4. Тест-кейс: Сборка фронтенда.

_Расскажи, как в первом этапе мы делаем `npm run build` (в образе на 1ГБ), а во втором просто копируем папку `dist` в легкий `nginx:alpine`._

### Выводы

- **Несколько `FROM` — это нормально.** Docker соберет все этапы, но сохранит только последний.
- **`COPY --from` — главная команда.** Она позволяет достать артефакт из любого предыдущего этапа по имени или индексу.
- **Безопасность.** В финальном образе нет исходного кода, менеджеров пакетов и лишних утилит — хакеру нечем будет поживиться.
- **Ускорение.** Вы можете кешировать этапы сборки отдельно.

### Вопросы

- В: Можно ли сделать больше двух этапов?
  - О: Да, сколько угодно. Например: 1) Тесты, 2) Сборка, 3) Линтер, 4) Финальный образ. Если тесты упадут на первом этапе, сборка дальше не пойдет.
- В: Куда деваются слои из этапа `builder`?
  - О: После завершения сборки они помечаются как ненужные и со временем удаляются (или висят как "dangling", если вы не используете `prune`). В итоговый образ они не попадают.
- В: Как запустить только этап сборки (например, для отладки)?
  - О: Используйте флаг `--target`: `docker build --target builder -t debug-build .`.

Готовы к объединению усилий? Блок 9: Docker Compose. Мы научимся запускать не один контейнер, а целую систему из приложения и базы данных одной командой.

## Блок 9: Docker Compose — Оркестратор на вашем столе

### Введение

- **Проблема «Портянки»:** Помните, сколько флагов мы вообще использовали постоянно? (`-p`, `-v`, `-e`, `--network`, `--name`) нам приходилось писать для одного контейнера. А если их пять? Docker Compose превращает эту «портянку» в структурированный YAML-файл.
- **Инфраструктура как код (IaC):** Объясни, что `docker-compose.yml` — это документ, который можно положить в Git. Новый разработчик скачивает проект, пишет одну команду и через минуту у него поднята вся среда.
- Есть ещё такая крутая вещь как `depends_on` и контексты сборки. Compose сам создаст сеть для всех сервисов внутри файла, так что им не нужно настраивать линки вручную.

### Текст для выступления

До этого момента мы работали как плотники с молотком: один гвоздь — один удар. Но современное приложение — это не только ваш код. Это база данных, кэш Redis, брокер сообщений и, возможно, фронтенд.

**Docker Compose** — это инструмент для описания и запуска многоконтейнерных приложений. Вместо того чтобы помнить все параметры запуска, мы записываем их в файл docker-compose.yml.

Одна команда — и Docker сам создаст сеть, скачает образы, создаст вольюмы и запустит все сервисы в правильном порядке. Это магия автоматизации, которая делает локальную разработку идентичной тому, что будет на сервере.

### Живое демо

1. Создаем структуру проекта.

Сделаем классику: Python-скрипт, который считает посещения в Redis.

```bash
mkdir compose-demo && cd compose-demo
# Напишем простой app.py
cat <<EOF > app.py
import time
import redis
from flask import Flask

app = Flask(name)
cache = redis.Redis(host='redis', port=6379)

@app.route('/')
def hello():
  count = cache.incr('hits')
  return f'Привет! Я обновлялся {count} раз.\n'

if name == "main":
  app.run(host="0.0.0.0", port=5000)
EOF
```

2. Готовим Dockerfile и зависимости.

```bash
echo "flask\nredis" > requirements.txt
cat <<EOF > Dockerfile
FROM python:3.9-slim
WORKDIR /code

COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

CMD ["python", "app.py"]
EOF
```

3. Пишем `docker-compose.yml`.

```yaml
version: "3.8"
services:
  web:
    build: .
    ports:
      - "5001:5000"
  redis:
    image: "redis:alpine"
```

_Заметьте: в коде Python мы обращаемся к хосту redis. Compose сам свяжет их по именам сервисов!_

4. Запуск

```bash
# Запуск всего стека в фоне
docker-compose up -d

# Проверка
curl http://localhost:5001

# Просмотр логов сразу всех сервисов
docker-compose logs -f

# Остановка и УДАЛЕНИЕ всего (сетей, контейнеров)
docker-compose down
```

### Выводы

- **YAML** — наше всё. Порядок, отступы и структура определяют вашу инфраструктуру.
- **Service Discovery.** Контейнеры внутри одного compose-файла видят друг друга по именам сервисов (`web`, `redis`, `db`).
- `up` / `down` / `stop` / `restart` — основные команды управления всем стеком сразу.
- **Build + Run.** Compose умеет сам собирать образы, если указан путь `build: .`.

### Вопросы

- В: В чем разница между `docker-compose stop` и `docker-compose down`?
  - О: `stop` просто останавливает контейнеры. `down` полностью удаляет контейнеры и виртуальные сети, созданные для них (но сохраняет вольюмы, если не указан флаг `-v`).
- В: Можно ли использовать разные Dockerfile для разных сервисов?
  - О: Да, в секции `build` можно указать конкретный файл: `dockerfile: Dockerfile.dev`.
- В: Что делать, если база данных запускается дольше, чем приложение, и оно падает с ошибкой подключения?
  - О: Флаг `depends_on` просто запускает контейнеры в нужном порядке, но не ждет "готовности" софта внутри. Профи используют скрипты типа `wait-for-it.sh` или настраивают ретраи (повторные попытки) в самом приложении.

Завершаем воркшоп? Остался Блок 10: Безопасность и Best Practices. Подведем итоги и научимся не делать фатальных ошибок.

## Блок 10: Безопасность и Best Practices — Спим спокойно

### Введение

- **Root в контейнере = Root на хосте:** если хакер «сломает» приложение, запущенное от root внутри контейнера, и найдет уязвимость в ядре, он получит полный контроль над всем сервером.
- **Минимализм:** Чем меньше утилит в образе (curl, git, стрелялки), тем меньше инструментов у взломщика.
- **ReadOnly Root Filesystem.** Если приложению не нужно писать файлы (кроме логов и вольюмов), запусти контейнер с флагом `--read-only`. Это мгновенно убивает 90% эксплойтов.

### Текст для выступления

Поздравляю, вы умеете собирать и запускать стеки. Но готовы ли вы доверить им свои данные и деньги компании? По умолчанию Docker запускает процессы от имени суперпользователя (root). Это удобно для обучения, но недопустимо в реальности.

Сегодня мы закроем три главные дыры:

1. **Пользователи:** Мы создадим обычного "работягу"-пользователя внутри образа.
2. **Гигиена данных:** Мы научимся использовать `.dockerignore`, чтобы секреты с вашего ноутбука (например, `.env` с паролями) случайно не улетели в публичный Docker Hub.
3. **Аудит:** Мы научимся проверять свои образы на наличие известных дыр в безопасности еще до запуска».

### Живое демо

1. Уходим от Root (USER).

Покажем, как создать пользователя и переключиться на него.

```Dockerfile
FROM python:3.9-slim

# Создаем системную группу и пользователя
RUN groupadd -r appuser && useradd -r -g appuser appuser

WORKDIR /app
COPY --chown=appuser:appuser . .

# Переключаемся! Теперь все команды ниже и сам старт приложения
# будут идти от имени бесправного appuser
USER appuser

CMD ["python", "app.py"]
```

_Проверка: docker run --rm my-secure-app whoami (должно вывести appuser, а не root)._

2. Чистота контекста (.dockerignore).

Покажем, как Docker тратит время на копирование ненужных папок.

```bash
# Создадим тяжелую папку, которая нам не нужна в образе
mkdir temp_logs && dd if=/dev/urandom of=temp_logs/big_file bs=1M count=100

# Создадим .dockerignore
cat <<EOF > .dockerignore
.git
temp_logs
*.pyc
pycache
.env
EOF
```

_Обратите внимание на размер "Context" при `docker build`. С игнором он будет в разы меньше._

3. Сканирование на уязвимости (Docker Scout / Trivy).

Современный Docker умеет проверять образы одной командой.

```bash
# Просканируем наш старый образ nginx или python
docker scout quickview python:3.9

# Или более детально по конкретным CVE
docker scout cves python:3.9
```

4. No-New-Privileges.

_Флаг запуска, который запрещает процессу повышать свои права (например, через suid бинарники)._

```bash
docker run --rm --security-opt=no-new-privileges:true alpine whoami
```

### Выводы

- Принцип наименьших привилегий: Всегда создавай пользователя `USER` в Dockerfile.
- `.dockerignore` — это не опция, а обязанность. Он защищает от утечки секретов и ускоряет сборку.
- Обновляй базовые образы: Регулярно пересобирай приложения, чтобы подтягивать патчи безопасности в `FROM` образах.
- Используй линтеры: Инструменты вроде `hadolint` проверят ваш Dockerfile на ошибки стиля и безопасности.

### Вопросы

- В: Что делать, если приложению нужно слушать порт 80, но обычный пользователь не может открывать порты ниже 1024?
  - О: Используй порты выше (например, 8080) внутри контейнера, а снаружи через `-p 80:8080` пробрасывай их куда угодно. Это стандарт практики.
- В: Безопасно ли монтировать `/var/run/docker.sock` внутрь контейнера?
  - О: НЕТ! Это дает контейнеру права бога. Он сможет управлять самим Docker-хостом, запускать и удалять любые другие контейнеры. Делайте это только если вы пишете инструмент для мониторинга Docker.
- В: Помогает ли Docker от вирусов-шифровальщиков?
  - О: Частично. Если вирус попадет в контейнер без вольюмов, он зашифрует только временные файлы. Но если у контейнера есть доступ к важным Volume или Bind Mounts — пострадают и они.
